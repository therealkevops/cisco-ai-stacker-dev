# The AI Stack: primitives mapped to the portfolio, in a Cisco, an NVIDIA and an open-source focus

A honeycomb map of the Cisco AI stack, in the manner of an ecosystem map. At the centre is the AI workload. Around it are the six primitives it needs, and beside each primitive sit the products that provide it: Cisco first, then partners, each primitive in its own colour.

| Primitive | Examples |
|---|---|
| Platform and runtime | NVIDIA AI Enterprise, Red Hat OpenShift, Nutanix, Kubernetes |
| Operations and agents | Splunk Observability, AI Canvas, ThousandEyes, AGNTCY |
| Security | AI Defense, Hybrid Mesh Firewall, Isovalent Runtime Security, Splunk ES, XDR |
| Network fabric | Nexus 9364E-SG2, Nexus 9000, Hyperfabric AI, Nexus Dashboard, Cisco Silicon One, UCS Fabric Interconnects, Isovalent Networking |
| Compute and accelerators | UCS C885A M8, C845A M8, UCS X-Series, Intersight, NVIDIA GPUs, BlueField |
| Data and storage | NetApp, Everpure (Pure Storage), VAST Data, Hitachi Vantara |

## Three focuses

A switch at the top of the panel changes the focus between **Cisco**, **NVIDIA** and **Open source**. Both use the same six primitives and the same honeycomb, with a different portfolio in each wedge. The NVIDIA focus has 52 entries and 150 integrations, taken from NVIDIA's own pages (nvidia.com, docs.nvidia.com, developer.nvidia.com, NVIDIA blogs and newsroom), and six reference architectures and designs: the RTX PRO, HGX (two) and NVL72 Enterprise Reference Architectures, DGX SuperPOD and DGX BasePOD. A few entries are Cisco's or partners' (Cisco UCS, Nexus N9100, Silicon One and AI Defense, storage and security partners, supported Kubernetes platforms), included only because an NVIDIA page names them. Cisco's AI POD 2-8-9-400 and 2-8-5-200 link to the NVIDIA reference architectures they are listed under, and the other way round.

A second check of Cisco's own pages in October 2026 added nine Cisco entries that earlier passes had missed: the 8223 router, Hypershield, Secure Access, the UCS C240/C245 and X580p, Unified Edge, Cloud Control, Data Fabric and Splunk AppDynamics. Cloud Control and Data Fabric are `check` entries, because Cisco ties neither to an AI POD design. Intersight Kubernetes Service was left out because Cisco has announced its end of life, and optics, ACI, Secure Workload, Multicloud Defense, Talos and Duo were left out because the sources did not tie them to Cisco's AI designs or because the wedge had no free cell.

The **Open source** focus has 46 projects, four published open designs or programmes (OPEA ChatQnA, llm-d's well-lit paths, the CNCF Kubernetes AI Conformance programme and NVIDIA's Confidential Containers reference architecture) and seven of the eight use cases; AI-assisted security operations is left out because no open project or published design covers it. Each project's licence, governance and latest release were read from its own LICENSE file, foundation page and release feed on 22 October 2026, and a second pass tried to disprove the descriptions. Here a filled hexagon is a foundation or community project, an open one is under an open licence but controlled by one company (Grafana, the NVIDIA and AMD libraries, Calico, Slurm since NVIDIA acquired SchedMD), and a dashed one is not under an OSI-approved software licence or its terms are not stated (open-weight models, the Ultra Ethernet specification). Models are called "open-weight", never "open source": none meets the OSI Open Source AI Definition. MinIO is included as a caution, since its repository is archived. Most use cases are drafts with no design, because open source publishes few validated designs; the assembly is yours to test. Vendor products show their open-source counterparts (Cilium for Isovalent, KAI Scheduler for Run:ai) and the reverse. The data is in [`src/data/oss.js`](src/data/oss.js), [`oss-details.js`](src/data/oss-details.js) and [`usecases-oss.js`](src/data/usecases-oss.js). Addresses carry the focus: `#/oss/product/cilium`.

The open-source focus is also used to show how hard it is to assemble one scenario from open parts. The enterprise RAG use case lists 34 projects across seven required decisions (document parsing, embedding server, vector store, orchestration framework, language model server, models and the platform), 28 separate owners, and a computed range of how many separately governed bodies one complete set of choices depends on. It also states that no project or foundation supports the whole stack, with the evidence: OPEA's documents name no support channel or SLA, Presidio says it has no official support, and only Prometheus lists commercial support providers, which add themselves. Licence and maintenance problems found while checking are on the map: TGI in maintenance mode, LLM Guard archived, Weaviate and Redis relicensed, Open WebUI and Phoenix not open source. Each of these 21 projects was checked against its own LICENSE file, README and release feed on 22 October 2026, but release dates for four of them come from GitHub's release pages, which could not be read exactly. A wedge with more than nine products now spills into further rings.

NVIDIA has no six-primitive taxonomy, so which primitive each NVIDIA product sits in is this app's choice, and where that differs from NVIDIA's own filing (NVLink under Data Center, DOCA under developer networking, Run:ai between Platform and Operations) the description says so. Eight customer use cases exist in both focuses, so each scenario can be read from either vendor's side and the two versions link to each other: an enterprise RAG assistant, a GPU cluster for enterprise AI, agentic AI assistants, secure private AI for regulated data, operating the AI factory, AI-assisted security operations, fine-tuning a model on private data, and a multi-tenant AI cloud for service providers and sovereign AI. Where the evidence is thin the use case is a `draft` with fewer required needs, and where no published design validates a scenario (NVIDIA fine-tuning) it lists none and every design can still be checked against it. In the NVIDIA focus each is checked against an NVIDIA document that is itself on the map as a design (for example the Enterprise RAG Deployment Guide), and each carries a `caveat` saying what to check. Addresses carry the focus: `#/nvidia/product/bluefield`, `#/nvidia/design/era-rtx-pro`.

## Using it

- **Pick a product** to read what it is for and its most useful features, each taken from the vendor's own documentation, with sources linked and a "Check" note where sources disagree or a feature is early access. It also lights up what the product connects to: the hexes it integrates with are outlined, and arrowed lines run the way each relationship does. A key on the map shows the line styles in view, the panel marks each connection with the same sample, and hovering a connection in the panel picks out its line. The panel lists the connections in words, and which validated designs include the product.
- **Pick a primitive** to read why it matters for AI and what to look for (background explanation, labelled as such), light up everything that provides it, and see which other primitives it integrates with most.
- **Pick a validated design** for the portfolio lens: the Secure AI Factory, the AI PODs and their 2-8-9-400 and 2-8-5-200 designs, and two Cisco Validated Designs for RAG pipelines (FlexPod with NetApp, FlashStack with Pure Storage). The products the design includes light up, each primitive shows how many of its products are covered ("2 of 6"), and the panel names the primitives the design leaves open. A CVD also shows its bill of materials as published, and lists what it uses that this map does not cover (for example the Webex chat bot or the Milvus vector database).

- **Pick a customer use case** (for example *Enterprise RAG assistant*) to outline the products the scenario needs: a solid outline for required, dashed for recommended. Then **check it against a design**. Every need the design meets gets a tick, every gap a plus, and the panel says in words how many required and recommended needs the design meets and what is still to find. Any design can be checked against any use case, so a design built for something else shows its gaps honestly (the 2-8-9-400 AI POD meets 6 of the 8 things the RAG use case requires, and is missing the X-Series servers and fabric interconnects the CVDs are built on).

Filled hexes belong to the focus vendor, open hexes are everyone else, and a dashed outline means the entry is not yet confirmed against a public page. Every selection has its own URL (`#/product/n9364e`, `#/primitive/security`, `#/design/ai-pod`, `#/usecase/enterprise-rag/flashstack-rag`), so the back button works and any view can be shared. Escape clears the selection, and every hex is reachable with the keyboard.

## Running it

```
npm install
npm run dev      # http://localhost:8999
npm test         # data integrity, honeycomb layout and portfolio coverage
npm run lint
npm run build    # static files in dist/, ready for Vercel or any static host
```

## Where the content lives

[`src/data/stack.js`](src/data/stack.js) holds the Cisco focus: the six primitives, the products and designs, and the integrations between them, each with a `status` of `sourced` or `check` and a source URL. Integrations are directional (a to b), so "Nexus 9000 contains Nexus 9364E-SG2" reads correctly from both ends.

- The NVIDIA focus is [`src/data/nvidia.js`](src/data/nvidia.js) (products, designs, links) with its descriptions in [`src/data/nvidia-details.js`](src/data/nvidia-details.js) and its source URLs in [`src/data/nvidia-urls.js`](src/data/nvidia-urls.js). Both focuses have the same shape, and [`src/data/model.js`](src/data/model.js) builds each into the lookups the map and panel use. A design's `related` field links it to a design in the other focus. A link marked `shallow` brings in its target but not what the target contains (a design that includes NVIDIA AI Enterprise has not necessarily used every part of it).
- To add a product, add an entry to `NODES` with its `primitive`, and at least one `L(...)` line to `LINKS`. A primitive's wedge holds up to nine products.
- [`src/data/details.js`](src/data/details.js) holds the fuller description, three to five named features, source links and any caveat for every product, and the background text for each primitive. Features are what the vendor states, not independent measurements. Anything unconfirmed, early access or in conflict between sources carries a `caveat`, and the tests fail if an unverified product has none.
- [`src/data/usecases.js`](src/data/usecases.js) holds the Cisco use cases and [`src/data/usecases-nvidia.js`](src/data/usecases-nvidia.js) the NVIDIA ones; the tests fail if a scenario exists in only one. Each lists the needs (one product, or several that are alternatives to each other) with a role of `required` or `recommended` and a reason, and the designs that are validated ways to deliver it. A use case is `sourced` when its required needs come from published design guides, or `draft` when they are an editorial reading and need review. Recommended needs are always editorial. A product can appear in only one need per use case.
- To add a validated design, add a node with `kind: 'design'` and "contains" links to what it includes. A design that publishes a bill of materials can carry `bom` (the lines as published) and `offMap` (what it uses that is not a product on the map). Coverage follows `composes` links downward, so a design that contains another design includes everything inside it. A product family and its models use a separate `models` link, which does not count: a design that uses the Nexus 9000 family has not necessarily used every model.

Line styles live in [`src/map/linkstyle.js`](src/map/linkstyle.js): nine relationship types collapse into six visual styles (structure, runs on, carries traffic, manages, secures, data flow), and a test fails if any type has no style or two styles look alike. The tests also fail if a use case names a product that does not exist, a design a sourced use case lists fails to meet one of its required needs, a link points at a product that does not exist, a product has no source, an integration reads the same from both ends, a primitive's products do not form one connected clump on the map, or a label is too long for its hexagon.

### Accuracy

Every use case was re-checked against its sources on 21 and 22 October 2026, with each claim marked confirmed, corrected or unverified, and the long vendor pages that earlier passes could only partly read were read in full where the site allowed. The corrections are in the data, and the tests pin the ones that mattered (for example that Hybrid Mesh Firewall on BlueField was announced, not shipped, and that the NVL72 reference architecture names Mission Control). Each use case now lists what to read next, published sizes, what the map does not cover, and questions to put to the vendor.

The NVIDIA entries were read from NVIDIA's pages through a summarising fetch tool, so wording is paraphrase and exact figures are worth checking against the linked pages before quoting. Roadmap items (Spectrum-X Photonics, Quantum-X Photonics, BlueField-4, STX and CMX, Sentry), the October 2026 NeMo Microservices sunset notice and pages that could not be read are called out in each entry's `caveat`.

Cisco renames and repackages products often, and some details in the public sources disagree (for example which ASIC is in the Nexus 9364E-SG2). Anything not confirmed is marked `check` and shows as unverified. Re-check before using this in front of a customer. Which primitive a product belongs to, and the order of the hexes, are editorial choices, not Cisco's.

## How it is built

React and Vite, with no other runtime dependencies. The map is a single SVG. Its layout, in [`src/map/hexgrid.js`](src/map/hexgrid.js), is pure geometry on a hexagonal grid and is tested without a browser. It is static files, so it runs on any static host, including the free tiers.
